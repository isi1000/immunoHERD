# Development code

This folder holds the code used to **build the training dataset and train the
models**. It is not needed to *use* HERD — for that, install the package
(`pip install immunoHERD`) and see the main README.

It is published so that the dataset and the models can be reconstructed from
scratch, and so that the curation decisions behind them are inspectable.

## Where the training data comes from

The training set has two sources, and they are not interchangeable:

- a corpus of **experimentally supported immunogens curated by hand from the
  primary literature**, recording for each antigen the assay, the source
  pathogen, the host sera and the original authors' selection rationale. This
  corpus is an original contribution of the work and enters the pipeline at
  step `01`, as `sequences_bibliographic.tsv`. It will be deposited on
  publication.
- **IEDB** records, restricted to B-cell assays, mined at step `00`. These
  complement the curated corpus rather than duplicating it: they are much
  richer in viral antigens, which gel- and array-based proteomics tend to
  under-sample.

Negatives are not curated at all. They are drawn from the reference proteome of
each positive's own source organism, length-matched, and filtered to remove
anything homologous to any positive in the dataset (steps `03`–`05`).

## Why there is no data here

This repository ships the *recipe* rather than the data: the scripts below query
IEDB and UniProt directly and rebuild the dataset. That avoids redistributing
third-party records, and it documents *how* the set was built rather than only
*what* came out of it. The hand-curated table is the one input that cannot be
regenerated by running the scripts; until it is deposited, step `01` has nothing
to merge and the pipeline produces the IEDB-derived part of the set only.

IEDB must be cited by anyone using data obtained through these scripts; see
https://www.iedb.org/citation_v3.php

## `dataset-construction/`

The pipeline runs per host species, in numbered order.

| Step | What it does |
|---|---|
| `00_mine_iedb_positives.R` | Mines IEDB for protein/peptide-level **positives** for a given host. |
| `01_integrate_bibliography.R` | Merges a manually curated bibliographic set (`sequences_bibliographic.tsv`) with the IEDB positives. |
| `02_collect_source_taxa.py` | Lists the distinct antigen taxa among the positives, with counts. Decides which proteomes to download and the threshold K. |
| `03_download_proteomes.py` | Resolves each antigen taxon with ≥ K positives to its UniProt **reference proteome** and downloads the FASTA into a shared cache. |
| `04_build_negative_pool.sh` | Builds the pool of candidate negatives from those proteomes. |
| `05_match_negatives.py` | Matches each positive to negative(s) from the real pool, by **taxon → lineage → length**. |
| `06_cluster_sequences.sh` | Clusters sequences by similarity, for the homology-aware split. |
| `07_make_cv_splits.py` | Generates **two** cross-validation schemes: homology-aware and leave-one-pathogen-out. Every fold acts as a rotating test set; there is no separate evidence-based test set. |
| `08_make_embedding_metadata.py` | Produces the FASTA of all curated sequences plus the master metadata with both CV columns, ready for ESM-2 embedding. |
| `09_check_bias.py` | Quality control: audits the curated set and the folds for shortcuts the model could learn instead of immunogenicity. |
| `10_fetch_host_immune_pilot.py` | Host-aware pilot: downloads one immune marker gene per host from UniProt (B2M by default). |

Two runners chain the steps: `run_pipeline.sh` for a single host (steps 02–09,
choosing species and negative:positive ratio), and `run_all_species.sh` for all
species at once, reusing a single global positives FASTA.

**Note on the environment.** Several scripts mention *Drago*, the HPC cluster
the pipeline was developed on, and a conda environment named `bioinfo`
(python3 + ete3, diamond, seqkit). Those comments record where each step was
run and what it needs — internet access for the UniProt downloads, none for
the rest — not a requirement to use that particular cluster.

**Note on the cluster steps.** `04_build_negative_pool.sh` and
`06_cluster_sequences.sh` carry SLURM headers (partition, CPUs, memory, time
limits) from the cluster they were run on. Adjust them for your own scheduler,
or run the underlying commands directly.

## `model-training/`

Two Colab notebooks:

- `Individual_model_training_canva.ipynb` — trains the per-species models
  (the six core hosts).
- `integrated_model_training.ipynb` — trains the pan-species model with 15
  species heads.

Both read the embeddings from Google Drive paths of the form
`/content/drive/MyDrive/IMMUNO_MODEL/...`. Those paths are from the original
working environment and will need adjusting.

The trained weights produced here are the `.keras` files shipped inside the
package, in `src/herd/models/`.
